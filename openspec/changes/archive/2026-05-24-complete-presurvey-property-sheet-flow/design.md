## Product Rule

這個 SR 的核心規則是：AIRE 第一階段產出的是房仲拿去談委託的物調表，不是補件後的正式完整檔案。

文字流程：

```
地址與屋主線索
  -> 地址定位與地政可查資料
  -> 物調表預覽與 PDF
  -> 現場詢問 / 圖資補件 / 手動修正
  -> 回寫物調表
  -> 後續正式說明書或合約資料
```

因此，地政有的資料要先放上去，但每個欄位必須有狀態：

| 狀態 | 意義 | 可出現在物調表 | 可當補件後正式確認 |
| --- | --- | --- | --- |
| 已帶入 | 地政或系統已取得基本資料 | 可以 | 補件後才可升級 |
| 待確認 | 有線索但需要屋主或現場確認 | 可以 | 不可以 |
| 需補件 | 系統沒有足夠資料 | 可以，以空白框或待補呈現 | 補件後才可以 |
| 查詢失敗 | API 沒有回資料或權限不足 | 可以，以失敗原因呈現 | 不可以 |

## UI/UX Boundary

本 SR 不大改 Fish 已調整過的 UI/UX。允許的變更只有：

- 修正重複入口、錯誤導向、不能點的假按鈕。
- 補上必要表單、資料狀態、上傳與 PDF 預覽。
- 修正欄位對齊、單位、狀態標籤與文字。
- 把不屬於當頁的設定移回設定頁。

禁止的變更：

- 重新設計左側一級選單。
- 大幅更換配色、版面骨架、卡片密度與導航模型。
- 把工作台重新拆成另一套新概念。

## Flow Design

### 1. 新增案件

新增案件只保留一個主要動作：輸入地址後先判斷地政資料。

- 如果地址可定位：建立案件，帶入土地、建物、門牌、候選地籍資料與查詢狀態。
- 如果地址不可定位：允許建立待確認案件，但必須標示查詢失敗與人工補正。
- 不再讓使用者在同一頁看到重複的地政查詢與新增案件流程。

### 2. 物調表

物調表是主要工作頁。它必須先顯示已取得資料，再讓使用者補缺口。

頁面分區：

- 案件摘要：地址、案件名稱、物件類型、目前費用、待確認數。
- 地政資料：已帶入欄位、待確認欄位、查詢失敗欄位、費用摘要。
- 補件與現場必問：同一表單內呈現，可填寫、上傳與加入補件清單。
- PDF 檢查：顯示哪些會進 PDF、哪些仍待補。

### 3. 補件

補件不是獨立重複工作台，而是物調表的缺口處理。

- 圖資上傳：地籍圖、空拍圖、格局圖、地標圖。
- 現場必問：建物現況、設備瑕疵、周邊環境、照片資料。
- 手動覆蓋：使用者可修正地政或公開資料帶入的候選內容。
- 回寫：補件後必須立即影響物調表預覽與 PDF。

### 4. 費用

費用要在物調表早期顯示，不是最後才顯示。

- 地政查詢成功：顯示服務名稱、筆數、單價、金額。
- 查詢失敗：顯示失敗原因與 0 元或地政實際回傳費用。
- 免費服務：顯示免費，不混成 AIRE 免費功能。
- 月累計：放在費用紀錄頁，工作頁只顯示本案本次費用。

### 5. PDF

PDF 可先產出物調表版本。

- 已帶入資料直接顯示。
- 待確認資料標示待確認。
- 缺圖資的欄位保留空白框。
- 格局圖若尚未產生，保留空白框，不放假圖。
- 不得使用假地址、假屋主、假實價登錄。

### 6. OPCOS 授權

測試版必須能完整操作；正式版由 OPCOS 授權與方案控制。

- AIRE 端保留授權序號驗證端口。
- OPCOS 端保留發序號與方案狀態端口。
- 測試版超級管理員可開啟全部開發中功能。
- 一般使用者看到開發中功能時，顯示目前正在開發中，不用方案控制話術。

## Implementation Contract

### Observable Behavior

- 使用真實瀏覽器輸入 `台南市東區裕農路288巷17號8樓之1` 後，系統可以建立物調表案件。
- 地政或 fallback 能取得的資料會進入物調表，不會因為尚未補件而被整份擋掉。
- 查不到的資料會標示待確認、需補件或查詢失敗，不會填入假資料。
- 物調表頁的按鈕都能操作；不能操作的項目不得呈現成可點按鈕。
- PDF 產出後可檢查地址、地政欄位、費用、圖資框與待確認狀態。

### Verification

- Spectra: `spectra analyze complete-presurvey-property-sheet-flow --json`
- Spectra: `spectra validate complete-presurvey-property-sheet-flow`
- Frontend unit tests: targeted Vitest suites for registry, case flow, PDF assembly.
- Rust tests: targeted land registry API/fallback tests.
- Browser E2E: non-headless or visible browser run through新增案件、物調表、補件、PDF preview/export.
- Artifact check: exported PDF saved under Downloads and manually/automatically inspected for wrong address, fake data, missing sections.

## Estimate

若不再大改 UI/UX，只補完整流程與後端，粗估如下：

| 階段 | 內容 | 估時 |
| --- | --- | --- |
| SR 收斂與現有 bug 固定 | 整理 active SR、鎖定 UI 不大改、列驗收清單 | 1-2 小時 |
| 地政資料與物調表資料模型 | 可帶入、待確認、補件、費用、來源狀態 | 4-6 小時 |
| 物調表/補件/PDF 串接 | 按鈕可操作、上傳回寫、PDF 空白框與狀態 | 6-10 小時 |
| OPCOS 授權端口 | 測試版可用、正式版保留授權與方案接口 | 3-5 小時 |
| 真實瀏覽器 E2E 與 PDF 驗收 | 裕農路地址、假資料清除、輸出檢查 | 3-5 小時 |
| 修 bug buffer | 依測試結果修正 | 4-8 小時 |

總計約 21-36 小時。若 API 憑證、OPCOS 端權限與部署環境都不阻塞，最快約 2 個完整工作天可以完成可驗收版；若要包含正式部署、序號發放與線上回歸，建議抓 3-4 天。
